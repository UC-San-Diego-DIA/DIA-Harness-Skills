# Reconstruct the OTBI semantics

Read this before turning lineage into database SQL. The catalog describes a report; its subject area's semantic model can supply behavior absent from the saved XML. Preserve all source expressions and raw XML in the conversion evidence. Do not normalize whitespace inside string literals, fix apparent spelling errors, merge differing value lists, or simplify overlapping categories without an explicit business decision.

## Establish the result contract

Record the analysis and requested view, all subject areas, visible and hidden columns, exact headings/order, formulas, criteria filters, selection steps, totals/subtotals, sorting, and prompt dependencies. Follow the requested output, using the sole flat table when unambiguous. Ask about tabular versus pivot/display output only when the request and source leave a material ambiguity. Hidden columns can affect aggregation and sort; hiding is not permission to delete them. View-level totals and display calculations may require an outer query or belong in the BI Publisher layout.

Oracle BI Server performs a distinct logical query even when DISTINCT is absent from the saved expression. This skill defaults to physical-row construction for attribute queries, so generate plain SELECT and record `row_policy: physical_rows`. Use `otbi_distinct` and SELECT DISTINCT only when distinct OTBI output is requested. Explain that different physical records can have identical projected values. Do not describe physical-row output as having identical OTBI duplicate counts. With requested DISTINCT, sort by projected expressions or aliases; do not copy hidden reference sort keys that would cause an Oracle selected-expression error. See the SELECT List Syntax section of Oracle's [Logical SQL Reference](https://docs.oracle.com/middleware/bi12214/biee/BIESQ/toc.htm).

Review success by physical field identity, join keys/types, input and result grain, filters, and calculations. Column positions, aliases, and ordinary ORDER BY differences do not by themselves fail that review. Align fields by the recorded mapping for comparison. Ordering that controls row limits, top-N, windows, or calculation stages remains part of the data logic. Explicit deduplication within source calculations remains part of their meaning; the output row policy does not authorize deleting it.

Read the full raw report XML and supplied issued logical SQL. Combined criteria, direct database SQL, hierarchy/drill columns, session variables, selection steps, custom SQL filters, row limits/top-N, calculations after aggregation, and references to other saved objects need explicit treatment. Do not silently reduce these to the first simple SELECT. Resolve external saved filters or other dependencies before making a runnable candidate.

## Grain and measures

Use current Oracle subject-area documentation to identify transactional grain and time linkage. Record what one input fact row and one output row represent, their underlying unique keys, and each measure's source expression, aggregation rule, currency, and units. A projected sequence number alone may not be unique; use documented composite keys or internal IDs to check join multiplicity separately from the requested projection. Repeated displayed values from different fact keys are legitimate physical rows. Repeated fact keys caused by a dimension join need investigation. Workbook lineage can identify a column without specifying sign changes, rate conversion, aggregation, or repository predicates. A bare Cost or Amount reference is not evidence that selecting the physical column without aggregation is equivalent.

Distinguish additive measures from averages, distinct counts, ratios, balances, and measures at a higher grain. Build GROUP BY from the intended logical result grain, not every mapped field. Put aggregate predicates in HAVING and row predicates in WHERE. Protect denominators and preserve source null behavior. Do not use SUM(DISTINCT amount) or blanket DISTINCT to hide join multiplication. When facts have different grains, calculate them separately before joining at the requested output grain.

Resolve measure definitions from the source, official documentation, and supplied model or physical-query evidence. Ask for additional issued logical SQL or source-model evidence only when a specific material definition remains unresolved; do not require the analyst to approve technical choices already supported by evidence. An OTBI result export supports reconciliation but does not by itself establish an unknown formula or security predicate. If required construction evidence stays incomplete, name the unresolved definition and keep the conversion blocked. An absent export alone does not block a complete candidate.

## Proceed without administrator logs

External dashboard prompts are normal runtime inputs. Record the user-confirmed selection, keeping the saved variable/default separate. Obtain the matching export at reconciliation; it is not required to use a confirmed runtime selection in the candidate. A default such as noData in the analysis's Advanced tab does not invalidate a dashboard export with a confirmed period. The schema-2 reviewed compiler accepts typed values with evidence and preserves the original report XML. It expands multiple selections into separate literals, never one comma-delimited string. Unset/All behavior still needs explicit evidence.

Use this investigation route only when a named material choice remains unresolved after source inspection and official documentation research. An administrator query log is helpful evidence, not a prerequisite for the skill. If the user lacks access, continue supported software work and official lineage research. Use a known-working physical reference when supplied; otherwise prepare a small read-only diagnostic that separates the unresolved source alternatives. Continue independent report construction while awaiting diagnostic results. Ask about available authoring surfaces only when the needed diagnostic depends on them.

Also check whether the user can select OTBI Performance Real Time through Create > Analysis. Oracle's [subject-area overview](https://docs.oracle.com/en/cloud/saas/sales/faoec/OTBI-Performance-Real-Time-SA-1.html) describes logical and physical database SQL information at execution/physical-query grain. This reporting route uses its own duty access and does not require the Administration > Manage Sessions UI. Inspect actual exposed fields; subject-area availability does not establish SQL-text field names or completeness. Narrow the export to the intended report/path and execution time, preserve all physical statements and identifiers for that execution, and record truncation. This evidence can resolve effective filters, source paths and joins before adding more physical-source hypotheses. If only execution statistics are available, use them to align the actual source analysis and prompt assets; do not claim to have obtained physical SQL.

Inspect captured SQL for completeness before using it as a reference. Preserve each row's report identity, date/time, query key, SQL length and available request metadata. A performance export may mix native SQL, ADF request XML and separate prompt/default executions. Trace derived aliases back to base columns instead of interpreting alias names as lineage. Complete source blocks can establish mappings and relationships even when a later calculation block is missing; they do not establish the missing final result.

If a long SQL field is clipped, obtain its actual presentation reference from Edit Formula or XML schema metadata. Measure LENGTH and export numbered short pieces using documented [logical string functions](https://docs.oracle.com/middleware/bi12214/biee/BIESQ/toc.htm), preserving row/query identity. Reassemble without trimming or separators and verify the original length and tail. Distinguish an export/display limit from truncation in the exposed field itself; chunking cannot restore already-discarded text. A calculation tail rebuilt from the source catalog is a labeled reconstruction, not a recovered original. Never append guessed SQL to make a truncated capture parse.

Use the authoring surface the user actually has. Standard OTBI's [SQL Issued box is read-only](https://docs.oracle.com/en/cloud/saas/otbi/otbi-user/advanced-techniques-examine-logical-sql-statements-analyses.html). For chunk-recovery columns, use Criteria > Edit Formula or provide a separate Analysis XML definition for Apply XML on a diagnostic copy when that editor is available. A generated logical SQL file is then a reference, not a request to edit SQL Issued. Validate XML expressions, scope filters, column IDs and table-view references locally; tenant acceptance remains a separate check. Do not replace the user's original analysis layout without authorization.

A diagnostic is a separately labeled investigation query, not a converted report candidate. Document all its relationships, filters, expected row grain, scope differences and question. It may intentionally expose several cost columns or line types without selecting one as the logical measure. Do not issue speculative joins or remove required report predicates to get a match. Use documented keys and EXISTS or independent aggregation to prevent multiplying item amounts by their distribution rows. Bound the query to the confirmed period and a relevant small project scope. Ask for the result export or exact Oracle error; do not ask the user to choose a mapping from technical names.

First compare the simplest measure at the intended grouping and period. Then compare category expressions and the full visible report. If the base measure is hidden, obtain a separate OTBI control result when needed rather than equating it to a differently defined displayed total. Identical amounts across currency/source alternatives do not resolve their lineage; use another discriminating slice or additional evidence. A single matching period establishes only that observed scope. Record unresolved access-policy parity separately. When evidence remains insufficient, retain BLOCKED and name the next comparison that can resolve it.

When a diagnostic executes but returns zero rows, prepare separate aggregate counts that still return zero-valued rows. Distinguish project visibility, period/date matching, item keys, lookup resolution and exclusions. Keep required report predicates unchanged in the report candidate; a broader date window is a labeled investigation slice only. Do not equate a dashboard fiscal-period label with a physical period-name column without evidence. An engine log can establish execution and processed-row counts; an EXPLAIN PLAN export supplies estimates, not actual rows at each predicate, even when its download is named SQL Monitor.

Oracle documents [how logical requests become secured physical queries](https://docs.oracle.com/en/cloud/saas/otbi/otbi-admin/tune-query-performance.html) and administrator access to session logs. The absence of those privileges changes the investigation route, not the user's ability to supply runtime values and result evidence.

## Logical functions need translation

| OTBI construct | Oracle construction and required evidence |
| --- | --- |
| IFNULL(x, 0) | Consider NVL(x, 0) or COALESCE after confirming datatype and evaluation behavior. Retain the original nesting and default location. |
| FILTER(measure USING predicate) | Conditional aggregation, commonly SUM(CASE WHEN predicate THEN row_measure END), only after establishing the measure's actual aggregate and source expression. Apply the predicate inside this measure, not to the whole query. |
| DESCRIPTOR_IDOF(display_column) | The underlying descriptor key, not the displayed number/name. Obtain its lineage or tenant metadata. Never compare an ID literal to a display column just because its heading says Number. |
| VALUEOF / presentation variables | Resolve effective session or runtime values explicitly; preserve access and unset-value behavior. |
| Logical SUM(... BY ...), REPORT_SUM, RANK, time-series functions | Reconstruct level, partition, order, time calendar, and aggregate stage with evidence. Do not pass these unchanged to Oracle. |

For two filtered measures subtracted from one another, preserve both predicates separately. Overlap may be intentional. A displayed Total may be the original measure rather than a sum of the displayed categories. Prove its definition from the source; do not replace it with an invented roll-up.

Oracle's [Logical SQL Reference Guide](https://docs.oracle.com/middleware/bi12214/biee/BIESQ/toc.htm) describes FILTER as conditional aggregation. Its example uses a summable measure; it does not establish that every mapped measure is SUM. Oracle's [double-column guidance](https://docs.oracle.com/en/middleware/bi/analytics-server/user-oas/create-parameter-that-uses-logical-sql-query-double-column.html) distinguishes descriptor values from descriptor IDs. Recheck these official references when translating.

## Scope, dimensions, and parity risks

Check code versus meaning, language translations, effective-dated records, calendar/period selection, business unit, ledger, currency, status/cancellation, and session context. Record source evidence for each restriction. Do not apply every generic restriction mentioned on a subject-area page to every fact branch without checking that it applies to this analysis.

Raw table access does not establish the same effective row access as the OTBI semantic layer. The analyst must establish how the database candidate preserves the relevant access scope. A hardcoded business-unit filter can define a comparison slice; it is not automatically equivalent to the user's OTBI authorization policy. Security uncertainty blocks broader equivalence claims and production use.

Keep each transformation's source expression, physical expression, workbook rows, additional Oracle evidence, aggregate stage, and review status in the existing plan/evidence record. Deliver complete SQL once required semantics and joins are resolved, then follow [validation-and-handoff.md](validation-and-handoff.md) for execution and comparison.
